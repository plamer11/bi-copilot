# BI Copilot 产品需求文档

> 面向 Amazon US 家居品类运营的**对话式数据分析 Agent**。  
> 用自然语言问「上个月退货率最高的 SKU 有哪些」，直接拿到结论 + 数据 + 图表建议，不用再写 SQL。

## 1. 背景与目标

运营日常要看销量、退货率、广告 ACOS、库存断货风险，但数据散在多张表里，  
取数得找数据同学排期，等一天是常态。BI Copilot 要做的是把这个链路缩到十几秒。

**成功标准**：运营提出的常见取数问题，能在一次对话内拿到可执行结论，且口径稳定（同一句话两次问结果一致）。

## 2. 目标用户与场景

| 角色    | 场景       | 典型问法                   |
| ----- | -------- | ---------------------- |
| 品类运营  | 周报复盘     | 「上个月销量最高的 5 个 SKU 是哪些」 |
| 广告投放  | 找出烧钱 SKU | 「哪些 SKU 的 ACOS 超过 50%」 |
| 售后/品质 | 定位质量问题   | 「退货率最高的 SKU 主要集中在哪些品类」 |
| 供应链   | 补货预警     | 「哪些商品快断货了，还能卖几天」       |

## 3. 功能需求

优先级：P0 = 核心链路，P1 = 安全与可信，P2 = 工程化与体验。**当前 12 项全部已实现。**

| 编号   | 需求           | 优先级 | 状态 |
| ---- | ------------ | --- | -- |
| FR1  | 自然语言转 SQL    | P0  | ✅  |
| FR2  | Schema 智能检索  | P0  | ✅  |
| FR3  | 指标口径治理       | P0  | ✅  |
| FR4  | 自愈环          | P0  | ✅  |
| FR5  | 安全守卫         | P1  | ✅  |
| FR6  | 人在回路（HITL）   | P1  | ✅  |
| FR7  | 结论生成         | P0  | ✅  |
| FR8  | 审计留痕         | P1  | ✅  |
| FR9  | 多轮上下文追问      | P2  | ✅  |
| FR10 | 语义召回通道       | P2  | ✅  |
| FR11 | CI 回归门禁      | P2  | ✅  |
| FR12 | 对话式前端（含审批面板） | P2  | ✅  |

### FR1 自然语言转 SQL（核心）

- 输入中文业务问题，输出可执行 SQLite 语句并执行
- 必须支持：多表 JOIN、分组聚合、Top N、时间范围过滤、比值指标、子查询、窗口函数
- **验收**：40 条标注集 execution accuracy ≥ 75%（难度分层统计）
- **实测**：87.5%（35/40），easy 12/12、medium 18/18、hard 5/10

### FR2 Schema 智能检索

- 8 张表 60+ 列不能全塞进 prompt，按问题检索出相关子集
- 中文问法要能命中英文列名（「广告花费」→ `ad_spend.spend_usd`）
- 双通道：关键词 + 同义词打分为主，embedding 语义召回为可选补充
- **验收**：gold SQL 用到的列召回率 ≥ 95%
- **实测**：整体 82.2%，**hard 档召回不足是准确率的主要瓶颈**（见 FR9 备注）

### FR3 指标口径治理

- 销量、销售额、退货率、ACOS、ROAS、毛利率、差评率等口径集中定义
- **验收**：同一句话连续问两次，结果完全一致

### FR4 自愈环

- SQL 执行失败时，把原始报错回灌给模型重写，最多 3 轮
- 用尽后诚实告知失败，不假装成功
- **验收**：人为注入列名错误的用例，1 轮内修复成功
- **实测**：40 条评测中 0 条触发自愈（首轮 SQL 全部可执行），该路径由离线测试覆盖

### FR5 安全守卫

- 禁止 DML/DDL、多语句、越权表、系统表访问
- 缺 LIMIT 自动补，超限自动收敛
- **验收**：12 类攻击语句 100% 拦截

### FR6 人在回路（HITL）

- 高风险查询（敏感表全量导出、SELECT *、多表无过滤）挂起等人工确认
- 支持 批准 / 改写 / 拒绝 三种决策
- 人工改写后的 SQL **必须重新过守卫**
- **验收**：挂起 → 决策 → 恢复全链路可用，拒绝时不执行任何语句

### FR7 结论生成

- 结果集 → 中文结论 + 业务建议 + 推荐图表类型
- 结果为空时明确说明，不编造数字
- **验收**：结论包含关键数字，且数字与结果集一致

### FR8 审计

- 记录每次提问的 SQL、执行结果、拦截与人工决策
- **验收**：可按会话查询完整事件流

### FR9 多轮上下文追问（第二轮补齐）

- 支持指代与省略：「上个月销量最高的 5 个 SKU」→「那 Kitchen 品类的呢」→「换成退货率最高的 3 个」
- 追问句先做**指代消解改写**成完整问句，再进后续节点
- 会话历史按 session 落库，可回溯最近若干轮
- **验收**：三连问真实 LLM 验证通过，第 2/3 轮正确继承上文约束
- **已知边界**：历史只影响改写，不参与 SQL 生成；超长会话不做摘要压缩（当前轮次上限足够）

### FR10 语义召回通道（第二轮补齐）

- Schema 检索除关键词通道外，增加 embedding 语义通道，用于关键词命中不了的口语化表述
- 后端可插拔三档：`local`（本地 BGE 模型）/ `api`（远端 embedding 服务）/ `hash`（无依赖确定性哈希兜底）
- 无 Key、无模型时自动降级到 `hash`，**保证 clone 下来就能跑**
- **验收**：三档后端各自可测，切换后端不污染缓存

### FR11 CI 回归门禁（第二轮补齐）

- 每次改动跑标注集，与基线比对后决定放行/阻断
- 门禁规则：新增失败用例 > 2 条，或任一难度档准确率跌幅 > 10%，判定为回归
- 基线快照入库，确认变好后手动刷新基线
- **验收**：规则本身有离线测试；GitHub Actions 上自动执行

### FR12 对话式前端（第二轮补齐）

- 单文件 HTML 页面，通过 SSE 消费后端事件流，实时显示每个节点进度
- 内置 HITL 审批面板：看到待确认 SQL 后可 批准 / 改写 / 拒绝
- **验收**：拒绝时不执行任何语句；改写后重新过守卫

## 4. 非功能需求

| 项    | 要求                                   |
| ---- | ------------------------------------ |
| 安全   | 数据库层面只读（纵深防御），不依赖模型自觉                |
| 性能   | 单次查询 < 5s（不含 LLM 生成时间），超 5s 强制中断     |
| 成本   | 单次提问 LLM 调用 ≤ 7 次，自愈 ≤ 3 轮           |
| 可观测  | 每个节点执行留痕，SSE 实时推送                    |
| 可移植  | 换 LLM 只改 `.env`，无需改代码                |
| 离线可测 | 测试不依赖 API Key，`pytest` 直接跑通（95 条全离线） |
| 可回归  | 准确率有基线快照，CI 自动判定是否引入回归               |

## 5. 明确不做（范围外）

- 不支持写操作（UPDATE/INSERT/DELETE），产品定位就是只读分析
- 不做图表渲染（只输出图表类型建议，前端自己画）
- 不做权限体系（假设使用人都是内部运营）
- 不做超长会话的摘要压缩（当前只保留最近若干轮原文）
- 不接真实数仓（数据是本地生成的 2.2 万行模拟数据）

> 注：首版 PRD 曾把「多轮追问」列为范围外，第二轮已实现，此条已移除。

## 6. 验收方式

```bash
python -m app.db.seed --force          # 建库
python -m app.eval.validate_golden     # 标注集自检：40/40 可执行
python -m app.eval.run_eval            # 准确率评测（需 Key）
python -m app.eval.ci_gate             # 回归门禁比对（离线，读上次结果）
python -m pytest                       # 离线测试套件：95 条
python -m scripts.smoke                # 端到端冒烟（需 Key）
python -m scripts.demo_multiturn       # 多轮追问真实链路验证（需 Key）
```

前端：启动后端后浏览器打开 `http://127.0.0.1:8000/`。

## 7. 当前指标快照

| 指标                 | 数值                                  |
| ------------------ | ----------------------------------- |
| 离线测试               | 95 条通过                              |
| 标注集规模              | 40 条（easy 12 / medium 18 / hard 10） |
| Execution Accuracy | 87.5%                               |
| Schema Recall      | 82.2%                               |
| 分层准确率              | easy 100% / medium 100% / hard 50%  |

**hard 档 5 条失败的归因**：全部是多表交叉 + 复合条件（如「既快断货还在投广告」），  
其中 3 条 schema 召回 100% 但 SQL 仍写错，说明瓶颈在**多表 JOIN 的推理能力**，不在检索。  
这是下一步优化方向，已记录在 README 待办里，未隐藏。
